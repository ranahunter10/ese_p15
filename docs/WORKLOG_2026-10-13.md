## Part 1 — The review cross-check, and a correction to the record

### 1.1 What the bug was

In `graph.py`, `trace_back()` walks the provenance graph backwards in time to
answer "what caused this?". The file branch looked like this:

```python
writes = [(ts, key) for ts, key, kind in cur.accesses
          if kind == WRITE and ts <= t and key in self.nodes]
if writes:
    ts, key = max(writes)              # last-write-wins (correct)
    w = self.nodes[key]
    if self._ident(w) not in seen:     # <-- the bug
        result.append((depth + 1, WRITE, ts, w.label()))
        queue.append((w, ts, depth + 1))
```

**Mechanism.** The walk is breadth-first and `seen` is marked when a node is
*popped* off the queue. Start at `cat`, depth 0. Its inputs are its parent
(FORK), the file it read (READ) and the file it executed (EXEC); all three go
on the queue at depth 1. The parent is popped first, so the parent's identity
enters `seen`. Then the file node is popped — and the file's last writer
turns out to be *that same parent*, because the ordinary shell shape

```bash
( cd $WORK && echo rel > p15_rel.txt && cat ./p15_rel.txt )
```

has the subshell write the file and its child read it. The writer is already
in `seen`, so the WRITE edge was never listed. The walk reported that `cat`
read a file and never reported who put the bytes there — which is the one
question a provenance tool exists to answer.

**The root cause is conceptual, not a typo.** `seen` was doing two different
jobs at once:

| job | correct? | why |
|---|---|---|
| don't **expand** a node twice | yes, and necessary | this is what guarantees termination |
| don't **list** a node twice | no | FORK and WRITE are *different causal facts* about the same process |

The guard had been copied from the endpoint branch, where it genuinely is
right — there it suppresses an edge that would restate the very link the walk
just traversed — but it was copied without the reasoning that justified it.

### 1.2 How it was proved, and when it broke

Three independent confirmations, in order:

1. **The regression test fails on the old code.** On v3.4b the walk returns
   `FORK bash(100), READ inode:8:77:1, EXEC /usr/bin/cat, FORK systemd(1)` —
   no WRITE.
2. **The VM evidence matches exactly.** The failing line from the 13-Oct run:
   ```
   FAIL | relative path linked through inode (write -> read)
        | FORK bash(14439), READ inode:8388609:419080:4054662292,
          EXEC /usr/bin/cat, FORK bash(9292), FORK sudo(9291)
   ```
   The `READ inode:…` edge is present, so the file *was* written and *was*
   read, by inode, exactly as designed. Only `WRITE bash(14439)` is missing.
3. **It is a v3.4 regression.** Unzipping the packaged v3.1, v3.2 and v3.3
   builds shows their file branch listed *every* write with no `seen` guard
   at all. The September runs prove it: their chains contain
   `FORK bash(2264)` **and** `WRITE bash(2264)` together. v3.4 introduced
   last-write-wins (a good change — it collapses 130 formal causes to 1) and
   the listing guard in the same edit, and the guard was the accident.

### 1.3 Correction to the v3.4a record — I had this wrong

the non-blocking-connect mistake. Reading the output line by line, that is

| `outbound connection attributed to the process that made it` | `socket.create_connection(addr, timeout)` sets the socket non-blocking, so the syscall returns `-EINPROGRESS`, never 0 — the monitor was right and the test's expectation was wrong | fixed in v3.4a (`net_demo.py` uses a blocking socket for the success case) |

The lesson I am recording against myself: two failures in the same run with a
plausible shared cause is not evidence of a shared cause. The per-check
evidence string was sitting there and distinguished them.

### 1.4 The fix: one rule instead of two guards

The walk now carries `via` — the `(node, edge_kind)` pair of the link it
arrived on — through the queue, and the rules separate cleanly:

- `seen` stops a node being **expanded** twice (termination, checked at pop).
- `via` stops an edge being **listed** as its own cause, which would only
  echo the step we came from (endpoint → the very process we reached it from).
- Nothing else is suppressed. An already-seen node reached by a *different*
  kind of edge is always listed.

Why this is equivalent to your patch for files, and better for endpoints: in
a backward walk a file is only ever entered via READ or EXEC, so the WRITE
candidate can never be the identical link — the behaviour is identical to
removing the guard. For an endpoint the incoming link *is* a CONNECT from a
process, so the rule still suppresses the echo your comment described. One
principle now covers both, and `trace_forward` uses it too, which fixed an
inconsistency: forward walks had been echoing the incoming CONNECT.

### 1.5 Why 147 tests missed it

The analyzer's synthetic "good run" made the writer and the reader
**siblings** (both children of pid 100). `vm_validation.sh` runs the subshell
form above, where the writer is the reader's **parent**. Siblings never
trigger the suppression; parent/child always does. Same syscalls, different
process tree, different code path.

Fixed by spawning the reader as a child of the writer (your patch). The proof
that it now bites: reintroducing the bug makes the analyzer's *own* test fail
with

```
FORK bash(212), READ inode:8:77:0, EXEC /usr/bin/cat, FORK bash(100), FORK systemd(1)
```

— structurally identical to the VM line, reproduced on a laptop with no
kernel involved. **The general rule: a synthetic scenario must reproduce the
validation script's process topology, not just its syscalls.**

### 1.6 The CLI gap, and a guard for it

been updated for v3.4: CONNECT events could not be filtered and nothing said

## Part 2 — Inbound telemetry: the `accept` / `accept4` hook (v3.5)

### 2.1 Why this, and why now

Objective O1 names lateral movement. With only `connect` hooked, lateral
movement was visible on one side: we could watch this host scan its
neighbours, but not watch this host *being* reached. A bind shell, an SSH
session arriving, a web server taking a request — all invisible. For a HIDS
that is half a sensor, and it is the cheapest remaining hole to close
because the graph already had the right shape for it.

### 2.2 Two kernel facts, established before any code was written

**Fact 1 — both syscalls are really used.** Under `strace`, in the same
container, same libc:

```
accept(3,  {sa_family=AF_INET, sin_port=htons(59524), ...}, [16])                = 4   # C, glibc
accept4(3, {sa_family=AF_INET, sin_port=htons(45192), ...}, [16], SOCK_CLOEXEC)  = 5   # Python
```

glibc's `accept()` issues `__NR_accept`; Python's `socket.accept()` issues
`__NR_accept4` (it wants `SOCK_CLOEXEC`). Hooking one would leave half the
servers on a box invisible with nothing in the output hinting at a gap. Both
are hooked — four tracepoints, not two. *(Measured here, on a newer kernel
and libc than the VM; the VM run will reconfirm rather than assume.)*

**Fact 2 — the kernel writes the peer address, during the syscall.** From
v5.4 `net/socket.c`, inside `__sys_accept4()`:

```c
if (upeer_sockaddr) {
        len = newsock->ops->getname(newsock, (struct sockaddr *)&address, 2);
        if (len < 0) { err = -ECONNABORTED; goto out_fd; }
        err = move_addr_to_user(&address, len, upeer_sockaddr, upeer_addrlen);
        if (err < 0) goto out_fd;
}
/* File flags are not inherited via accept() unlike another OSes. */
fd_install(newfd, newfile);
err = newfd;
```

Three consequences, all load-bearing:

1. At syscall **entry** the buffer holds nothing useful, so the address must
   be read at **exit** — the opposite of the connect hook, which reads at
   entry on purpose.
2. On a successful return the copy is *guaranteed*: a failure in
   `move_addr_to_user` jumps to `out_fd` and the whole syscall fails. Reading
   the buffer only when `ret >= 0` can never read garbage.
3. **The writer is the kernel, not the process.** A monitored process can lie
   about who it connects *to*; it cannot lie about who connected *to it*,
   because that string came from the kernel's own socket state. This is the
   first value in the system with that property, and the one an enforcement
   layer should prefer to act on.

### 2.3 Design decisions

| # | Decision | Reasoning |
|---|---|---|
| B1 | Hook `accept` **and** `accept4`, enter and exit | Fact 1. |
| B2 | Read the peer at **exit**, only when `ret >= 0` | Fact 2. |
| B3 | A failed accept is **dropped in the kernel** | `-EAGAIN` fires on every poll of a non-blocking listener, `-EINTR` on every signal: no peer exists and no buffer was written. That is an *absence*, not an attempt. Exactly the opposite of a refused `connect`, which is kept because a burst of refusals is what a port scan looks like from inside the host. The asymmetry is in what the failure *means*. |
| B4 | An inbound endpoint is keyed `host:<addr>` — **no port** | See 2.4. |
| B5 | Reuse `net_t` with a direction flag, not a fourth record type | "Who, when, which socket, which peer" is the same set of facts both ways. Record layout, size (256 bytes) and the decode path are unchanged; `NET_FLAG_INBOUND` picks the handler. |
| B6 | `accept` stashes live in their **own** LRU map | See 2.5. |
| B7 | `ACCEPT` is a distinct edge **kind**, traversed exactly like `CONNECT` | See 2.6. |
| B8 | No peer name → say so (`NET_FLAG_NOPEER`), never invent one | `accept(fd, NULL, NULL)` is legal and common, and a unix client normally has no bound address, so `getname()` returns only the family. Reporting `0.0.0.0` would be a fact the kernel never stated. |
| B9 | Inbound and outbound to the same host are two nodes | `host:10.0.0.9` and `net:10.0.0.9:443` are different relationships with the same counterparty; merging them would read as one. |

### 2.4 Mechanism: why an inbound endpoint has no port

When a client connects, the kernel assigns it a source port from a random
high range. The address `accept()` hands back describes the *peer*, so the
port in it is that ephemeral number — different on every connection:

```
accept4(3, {sin_port=htons(45192), sin_addr="127.0.0.1"}, ...)   # connection 1
accept4(3, {sin_port=htons(51022), sin_addr="127.0.0.1"}, ...)   # connection 2
```

Both are the same peer. Keying the endpoint node on `addr:port` would mint a
fresh node per connection: 500 connections from one host would be 500
singleton nodes, and "who keeps connecting to this box" would be
unanswerable. This is the dependency-explosion problem appearing in a new
place, and the cure is the same kind of cure as last-write-wins for files —
identify by the thing that is stable.

Outbound keeps its port (`net:10.0.0.9:443`) because there the port is the
*service*: stable, and half of what identifies the peer.

What we lose: which of *our* ports the peer reached. In practice the
accepting process implies the service (`sshd` means 22), but the kernel's own
answer needs `sock:inet_sock_set_state` — the next piece of work.

### 2.5 Mechanism: why accept gets its own map

Both hooks are split enter/exit, so each needs to stash state between the
two halves, in an LRU hash keyed by `pid_tgid`. An LRU evicts the **oldest**
entry when full.

A listener can sit blocked inside `accept()` for hours — that is what `sshd`
does all day. If connect and accept shared one 16 384-entry map, ordinary
outbound churn would walk right past that blocked entry and evict it, and
when the connection finally arrived the exit probe would find no stash and
emit nothing. The inbound connection we care most about is exactly the one a
shared map is most likely to drop.

A separate map means only other accepts can evict an accept. Cost: ~256 KB of
kernel memory. (Design applied and reasoned; not yet tested under churn —
that needs a soak test.)

### 2.6 Mechanism: edge direction, and why ACCEPT is traversed like CONNECT

A TCP connection carries data both ways whichever side opened it:

- a bind shell **accepts** a connection and then sends files out through it;
- an HTTP client **connects** out and reads a payload in through it.

So both kinds are followed in both directions of a walk, and the *label*
preserves which it was. Keeping them as separate kinds matters because the
two readings are opposite findings for a detector: `CONNECT` to a strange
address is possible exfiltration, `ACCEPT` from a strange address is possible
arriving lateral movement. One graph, one traversal rule, two labels.

## Part 3 — The adversarial review, and what it found

Three findings, all reproduced on the pristine v3.5 tree before anything was
changed. Full rows in `CHANGES_v3.5.md` §C2 (rows 99–108); the mechanisms
are here.

### 3.1 H1 — an effect that predates its cause

`trace_forward` tested `ts >= t` on files and connections but not on
children. So a walk that reached a process *through* a file read at 50 s
would list that process's child, forked at 41 s, as an effect of the read.
Nine seconds in the wrong direction is enough to invert a causal story.

Fix: the FORK branch checks the bound like every other branch. One line, and
the forward law now holds on every branch without exception.

### 3.2 H2 — the one that returned a wrong answer

This is the serious one. `seen` was keyed on the node alone, so a file was
expanded **once**, at whichever time bound reached it first. Consider:

```
W1 writes F @50s      R reads F @100s      W2 writes F @200s      R reads F @296s
```

Walking back from R, the file is expanded at bound 100 s, finds W1 under
last-write-wins, and is then marked seen. The 296 s read never gets
expanded, so the walk says: *the bytes R read came from W1*. They came from
W2. That is not a missing edge, it is a confident falsehood, and it is the
one failure mode a provenance tool cannot have.

**Why the node alone was the wrong key.** Under last-write-wins, a resource
reached at two different times is two different questions with two different
correct answers. So the visited state is `(node, bound)`, not `node`. A
wider bound does *not* subsume a narrower one here — `max(writes ≤ bound)`
changes with the bound — which is exactly why the obvious optimisation
("only re-expand when the new bound is wider") would have been wrong, and
why I did not take it.

Termination still holds, and for a sharper reason than before: bounds come
only from timestamps already in the graph, so the state space is finite and
each state expands once. A `listed` set keyed `(source, kind, ts)` keeps
re-expansion from printing the same fact twice, and `max_visits` bounds the
*work* for the pathological shape — one file written and read 400 times
alternately — where deduped edges could otherwise keep the queue busy
without the result growing.

### 3.3 H3 — arrival order leaking into timestamps

`_touch()` maintained `last_ns` and never lowered `first_ns`, which was set
from the first record *processed* for a node. Per-CPU perf buffers deliver
out of order across CPUs — the entire reason `ExecAssembler` exists — so the
first record processed is routinely not the earliest record that happened. A
300 s event arriving after a 500 s one left `first_ns` 200 s too late, and
`process()` had the same gap because it updated `last_ns` inline rather than
through `_touch`.

Two things then broke, and the review named both. A third, below, it missed.

**Where I went further than the proposed fix.** The FORK edge used
`first_ns` as its timestamp, so an inflated `first_ns` could place a cause
after the point being asked about. The review's fix clamps it to the bound,
which satisfies the law but reports the bound as though it were a
measurement. The better answer was already in every record: `task->start_time`,
the kernel's own fork time, in the same CLOCK_MONOTONIC as the event
timestamps, and provably no later than any event of that process. So
`_fork_ts()` returns the real fork time when it is exact, falls back to
`min(start_ns, first_ns)` for a /proc-estimated start, and clamps only as a
last resort. In the test case the edge now reads **10 s** — the truth —
where the old code said 500 s and the clamp would have said 300 s.

**The fourth consequence, still open after the review's three fixes.** An
inferred exit — a PID reused with no exit event — stamped
`old.exit_ns = node.first_ns` at the moment the new generation appeared.
Lowering `first_ns` afterwards leaves that stamp stale: in my test the old
generation looked alive 490 s longer than physically possible. The right
bound is the new generation's fork time, because a PID is not handed out
again until its previous holder is gone. Same helper, same proof, one more
place. Found by a test written for this round, not by the review.

### 3.4 The two design notes, both acted on

**Endpoints were uncapped.** Files have had an LRU cap since v3.2. Endpoints
did not, which was defensible while only our own processes could create them
— and stopped being defensible the moment inbound landed: any host that can
reach a listening socket can mint a `host:<addr>` node. An uncapped map is
then memory growth driven by a remote party, inside the monitor. Now
`--max-endpoints` (default 200 000), same LRU as files, counted in
`stats["evicted_endpoints"]`.

**Point-in-time queries.** `at_ns` added to both walks: "what had caused
this as of 14:32" is the question an analyst holding an alert timestamp
actually asks. One correction to the review's framing, for the record:
nothing was removed in v3.4. `before_ns` has always been an internal
parameter of `_in_edges`, and `trace_back` never exposed a time bound in
v3.1, v3.3 or v3.4 — checked against the packaged builds. Good suggestion,
wrong history.

### 3.5 How these fixes were checked

- Each of the four fixes was **mutation-checked**: reverted one at a time,
  confirming which test fires. H1 → 2 tests, H2 → 1, H3 → 3,
  `_fork_ts` → 2.
- A **fuzz test** (5 seeds × 15 trials) builds a graph from fully shuffled
  record arrival and asserts, on up to 20 walk roots per trial: no cause in
  the future, no effect before its cause, and `first_ns ≤ every event seen`.
  It independently catches H1, H3 and the `_fork_ts` regression.
- `tests/test_adversarial.py` holds these 14 tests, kept apart from
  `test_graph.py` because they are written from the attacker's side of the
  contract: not "does the feature work" but "can I make the walk tell me
  something false".

**What is not reconciled.** The review's `p15_v35_hardening.patch` and its
17-test file were not attached — only the document. These fixes were written
from the findings' descriptions after reproducing each bug locally, so the
trees differ: 178 tests here against 181 reported there, and three of those
17 tests are unaccounted for. The patch should be merged and the test sets
de-duplicated when it arrives.

## Part 4 — The rating round: closing the P1 list

The rating (8.5/10 as a research prototype; 4/10 on overhead, unchanged and
correctly the only score that matters until the ladder runs) came with a
catalog rather than new bugs. Rows 109–116 in `CHANGES_v3.5.md`. Four of
the items are worth the mechanism, because two of them were filed one
category lower than they deserved.

**`host:::1` was filed as cosmetic. It is a parsing bug.** An id has to be
splittable back into scheme and address — by a person typing it into
`talkers`, or by us parsing it later. `host:::1` is not; `host:[::1]` is,
and brackets are what the outbound id has always used.

**The endpoint cap default was a guess, so I measured it.** With
`tracemalloc`: ~380 B per EndpointNode with one access, ~2.4 KB with
twenty; FileNode ~530 B / ~2.6 KB. The 200 000 I had copied from the file
cap would be 76–476 MB of endpoints — larger than the monitor's entire
measured RSS. The default is now 25 000 (~9 MB typical, ~59 MB worst), the
measurement is in `ARCHITECTURE.md` §7, and a test keeps the number and the
documentation from drifting apart.

**The same measurement indicts a default I did not touch.** `--max-files
200000` implies 106–516 MB against a ~135 MB measured peak RSS: that cap is
not a safety bound, it is larger than the machine. Lowering it to ~50 000
would make it one and would cost forensic history on a file-heavy host.
That is a decision about what the tool *remembers*, so it is written up as
an open question rather than committed quietly.

**`max_visits=4000` is validated, not justified.** On the pathological
3 000-touch file the walk takes ~3 ms at the default and ~5 ms at 100 000,
because `max_items` binds first. So the budget is a backstop against a
shape nobody has thought of, not a performance lever — and the test asserts
that shape (25× the budget changes nothing material) rather than a
millisecond figure that would go flaky on another machine.

Also closed: `--at` is now on `query_graph.py trace` and `impact`, so the
point-in-time query is reachable by an analyst rather than only from
Python; three test classes were added for the gaps the rating named
(PID-reuse isolation at the walk level, a child seen before its parent, and
an order-equivalence test asserting that the same events fed forwards and
reversed give *equal* answers); and the `accept_enter` re-entry case is
documented in the kernel source.

One of those new tests failed on my own wrong expectation — I assumed a
placeholder would adopt a later `comm`, when the late-rename guard from
Journal row 12 deliberately prevents exactly that. The code was right; the
test now records the rule.

**Still open, and now with numbers attached:** everything in the rating's P0
list is a VM run. 23 analyzer checks and the 0/2/4/6/12 ladder have never
executed on kernel 5.4, and the `accept` code — the headline feature — has
never run against a real BPF verifier.
